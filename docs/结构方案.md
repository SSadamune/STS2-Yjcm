# 一将成名：单工程双版本与 GitHub 规整方案

状态：2026-10-11 已完成单工程迁移，公开源码仓库为 https://github.com/the-cdphantom/STS2-Yjcm 。本文保留迁移前的方案与比较数据；实际目录、检查结果与恢复方式以 [迁移验收](迁移验收.md) 和 [README](../README.md) 为准。

## 结论

推荐一个独立仓库、一个 Godot 业务工程、一套业务源码，同时构建 stable 与 beta。
加载器和测试仍可保留各自的小型辅助 csproj；它们不是重复的 Mod 业务工程。
两个版本是游戏 API 兼容目标，不是 Debug/Release，也不建议强行合并成一个内容 DLL。

现有 `威董卓开发/WuZhugeliang.csproj` 已经通过 Variant 参数完成两版构建，因此构建方式已验证；待完成的是源码/资源/脚本真正归并。
两套公共 YjcmCode 当前各有 208 个 C# 文件，stable 对照 beta 有 161 个逐字相同、47 个不同。47 个是文件字节差异，不代表 47 个 API 冲突：包括格式、注释、编码、实际 API 适配以及潜在实现差异。

## 仓库边界与目录

建议仓库根目录 `E:\sts2mod\Yjcm`，不把整个 `E:\sts2mod` 当仓库上传。

## 双版本实现方式

1. 用一个 `GameApiVariant=stable|beta` 参数决定编译依赖及 GAME_BETA 符号；分别引用固定快照，不引用当前 Steam DLL 自动漂移。
2. 相同源码只保留一份。对 47 个差异文件逐一复核，区分真正 API 差异与业务行为差异；不能用任一版本整体覆盖另一版本。
3. 大量出现的 API 差异集中在 Compatibility，例如攻击命令 stable 的 `FromCard(this)` 与 beta 的 `FromCard(this, cardPlay)`，以及 Damage 的参数签名差异。调用方写同一份卡牌效果。
4. 兼容助手必须保留 cardPlay、choiceContext、伤害 ValueProp、来源和返回值的原语义，不能只做到“编译不报错”。少量虚方法签名差异用局部 #if GAME_BETA，必要时选入同名 stable/beta 实现；不保留第二套整目录。
5. WEI_DONG_ZHUO 目前主要用于隔离历史内容包；正式合并后两角色始终包含。逐处审计后移除该历史分包开关，不盲删条件编译；GAME_BETA 保留。
6. 生成器迁移到 tools，调整为读取统一模型/设计数据。董卓复制卡的游戏 ID、卡框、卡池、描述和音效仍保留；不能因为“统一源码”就把角色专属复制卡直接替换为原卡。优先产出版本无关生成代码，差异经 Compatibility 处理；无法统一的生成片段暂按版本隔离并逐步减少。
7. generated 文件建议初期随源码提交并由 CI 校验可重现性；未来再考虑只提交生成源并自动生成，避免同时改变过多流程。
8. 初期构建仍顺序进行。分别隔离 obj、bin、NuGet 项目缓存和生成器临时目录后，才考虑并行。

建议对外命令（拟新增，不是现在可直接运行的脚本）：

```powershell
pwsh ./tools/build.ps1 -Variant stable
pwsh ./tools/build.ps1 -Variant beta
pwsh ./tools/build.ps1 -Variant all
pwsh ./tools/package.ps1
pwsh ./tools/deploy.ps1 -GamePath 'E:\SteamLibrary\steamapps\common\Slay the Spire 2'
```

build 只构建/验证；package 生成一个完整统一包；deploy 单独显式执行并检查游戏关闭。GitHub CI 不部署本机，也不自动发布 Workshop/GitHub Release。
输出隔离属性需在 Directory.Build.props 等足够早的位置设置，并验证 Godot SDK 实际输出、导入和调试仍正确，不能只修改 OutputPath。
参考：[Microsoft 的 MSBuild 文件夹级配置说明](https://learn.microsoft.com/zh-cn/visualstudio/msbuild/customize-by-directory?view=visualstudio)。

最终包继续保持：

```text
yjcm/
├─ Yjcm.dll                            # 装载器，程序集身份 Yjcm.Loader
├─ Yjcm.0.107.1.dll                    # stable 内容程序集，身份 Yjcm
├─ Yjcm.0.111.0.dll                    # beta 内容程序集，身份 Yjcm
├─ Yjcm.pck                            # 一份共用完整资源包
├─ mod_manifest.json
├─ Voice/
├─ Spine/
└─ MeshAnimation/
```

沿用现有加载器按宿主版本选 DLL 的规则；重构前后进行加载器/依赖版本测试。
公共类型 `Yjcm.Api.PublicApi, Yjcm`、`Yjcm.Api.YjcmPublicApi, Yjcm` 与反向代理不改名。
加载器保持独立程序集，不为“一个项目”把它塞入同身份内容 DLL。

## 原目录如何归并

| 旧位置 | 新位置/处理 |
| --- | --- |
| 正式版、wuzhugeliang 的公共源码 | mod/src 一套；差异归入 Compatibility |
| 威董卓开发的角色、新牌、事件、遗物和视觉 | 同一 mod/src，按内容类别/角色分组 |
| 正式版资源 + resource_pack 的覆盖资源/本地化 | 合并到 mod 下，显式处理覆盖冲突，消除两层 PCK 叠加依赖 |
| 正式版/loose_assets 的 Voice、Spine 等 | assets/loose，只有一个运行素材来源 |
| 各版本重复本地化 | 每个表一份，不再依赖开发目录覆盖；校验键冲突和跨引用 |
| feature_beta | 收敛为少量 API 适配，不保留整套复制业务代码 |
| 编译依赖/YjcmLoader | loader |
| 当前生成/发布/验证脚本 | tools + tests；删除“test 等于董卓完整包”的命名歧义 |
| 武诸葛亮遥测/mod | mod/src/Telemetry |
| 遥测 Worker、仪表盘 | telemetry，部署凭据仍留本机/密钥服务 |
| 联动接口、联动源码交付、设计与教程 | docs；交付 ZIP 为本地产物，不重复纳入源码 |
| 三国杀/威董卓开发包、DLL、PCK、日志 | artifacts/dist 与 artifacts/logs，忽略入库 |
| 素材原件、用户日志、备份、下载软件、其他 Mod | 保留在仓库外，不整体搬入新仓库 |

不在第一轮顺便重命名所有类、命名空间、模型 ID，亦不把其他 Mod 并入此仓库。

## GitHub 入库范围

提交：自有源码、csproj、project.godot、必要场景/配置、本地化、生成器与设计输入、测试、文档、可公开的运行资源、依赖版本配置、锁文件与校验清单。
不提交：sts2.dll 及游戏原版 DLL、缓存/编译产物、整个游戏提取目录、历史备份、玩家日志/存档、程序安装包、node_modules、个人路径配置、遥测实际数据、Wrangler 登录缓存与 API token。

依赖清单改为可移植版本号/文件名/哈希，不把现有绝对本机 source 路径原封不动公开。提供开发者依赖准备说明/校验工具；不从其他网站自动下载原版游戏 DLL。
`GodotPath`、`GamePath`、私有素材路径改为参数、环境变量或忽略的 `build.local.json`，附可提交的示例配置；不得把 CDphantom 个人目录或当前盘符作为构建前提。

运行素材应先审查公开范围。代码许可证由作者确认；第三方游戏素材、AI 素材、Spine/音频来源与工具许可证分别记录，不用源码许可证笼统覆盖全部素材。
若只公开源码，对未公开资源给出 manifest、获取/导入方式、缺失时的明确诊断；不要声称单独克隆源码就能完整打包。

当前完整 PCK 实测约 241.3 MiB，本身就不适合提交为普通 Git 文件。GitHub 普通 Git 阻止超过 100 MiB 的文件；大型且允许公开的运行资源可选 Git LFS。LFS 不能代替权限/素材公开范围审核，也不用于备份、缓存或原版 DLL。
参考：[GitHub 大文件说明](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github)、[Git LFS](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-git-large-file-storage)。
用户现有 Mod 公告仍声明成品仅通过 Steam Workshop 免费发布，因此 GitHub 初期定位开发源码与文档；公开可下载的完整成品需另行确认，不能擅自新开发布渠道。

## CI 和验收

公开 CI 先执行无需游戏二进制的静态检查：格式、本地化、生成器一致性、资源 manifest 与公开接口声明检查。
真实双版本编译和依赖游戏 DLL 的回归须在持有固定依赖的授权环境运行；不能假设普通 GitHub runner 自带 sts2.dll。全链构建初期维持本机手动流程；若以后用私有 runner，只对受信任/明确批准的代码开放，不自动执行外部 PR 的代码。

验收要求：

- 从干净的新 checkout，按照文档准备固定依赖和允许分发的资源后，能分别构建两版和完整包；不再依赖旧三个工程目录。
- 所有 ID、卡池、标签、已有存档相关字段、本地化键和公共 API 类型保持；董卓和武诸葛内容均存在。
- 两版程序集隔离、规则回归、火攻/装备接口、裂穹 UI、特效与资源审计继续通过。
- 加载器、两 DLL 和 PCK 的最终包组合正确；游戏内至少验证两角色、存档、特效开关与联动代理。CI 通过不能替代实际游戏/联机验证。
- Git 入库扫描排除大型产物、敏感数据、绝对个人路径和不应公开的第三方二进制。
- 最终仅部署 mods/yjcm，游戏运行时不覆盖，不改其他 Mod。

## 执行顺序与回退

第一阶段：在新独立目录搭骨架，保留旧工程作对照，只迁入必要源码与资源，重写相对路径与配置；不删除旧工程。
第二阶段：逐个归并差异和本地化/资源，使用单工程两版构建；有独立版本编译与回归基线，不混入新的玩法调整。
第三阶段：完整包与真实游戏验收，再准备 Git 清单、README、依赖/资源说明及 CI；未获确认不创建远程仓库、不推送。
第四阶段：用户确认新工程可替代旧工程后，才按精确目录清理旧工程/旧脚本。先建立小型源码级回退快照；不再对整个工作区做几十 GB 的重复备份。

本方案建议：接受“一个业务工程双 API 构建”，不继续保留正式版、测试版、董卓扩展三套独立维护的业务源码树。
